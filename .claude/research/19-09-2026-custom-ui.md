## Short answer

- **Use normal Unity UI (uGUI) with TextMeshPro text, built in code.** The game's own UI uses the
  same system. (verified in ValheimTomrer)
- **Many needs don't require a window.** The game already has messages, hover text, map pins, popups,
  the build card, the key hints row and a text journal we can fill.
- **An own window takes:**
  - its own canvas
  - the game's sprites and font, with **own copies of the font's material** (corrected: sharing the
    HUD's material makes small text read grey)
  - **nine** small patches that stop the game from reacting while it is open (corrected: the first
    plan had four)
  - care with the pad: the game's UI module also reads a real pad
- **No Jötunn needed.** Everything here is client-side and adds no prefabs or pieces.

**The template's kit** already has the parts every window needs:

| File | What it holds |
|---|---|
| `src/Ui/ModUi.cs` | the one "our window is open" flag every input patch reads, with one extra frame after closing |
| `src/Patches/InputBlockPatches.cs` | the nine input patches |
| `src/Ui/UiTheme.cs` | the game's font, own copies of its text material, the UIAtlas sprites; rebuilt after a world load |
| `src/Ui/UiBuild.cs` | the canvas recipe below (`UiBuild.Canvas`), small widget builders, and the text box that is safe on a pad |
| `src/Patches/BuildUiOnLayoutChangedPatch.cs` | keeps a typing text box selected when the player switches between keyboard and pad |
| `src/Ui/PadGlyphs.cs` | the game's controller icons as `Sprite`s |
| `src/Input/GamePad.cs` + `src/Patches/ZInputTryGetButtonStatePatch.cs` | the pad through the game's button names, and holding a combo's buttons back from the game |
| `src/Example/ExampleWindow.cs` | a small working window that uses all of the above, with its autotest (`example_window`) |

## Which UI system

| System | Works here? | Effort | Use for |
|---|---|---|---|
| **uGUI + TextMeshPro, built in code** | Yes. Same system as the game (verified in ValheimTomrer) | Medium | **All UI the player sees** |
| IMGUI (`OnGUI`) | Yes | Low | Debug overlays only. Looks like plain Unity, not Valheim. Clicks also reach the game. |
| UI Toolkit | Maybe. The game ships no theme and no default font | High | Not recommended |
| Asset bundle with UI prefabs | Yes, if built for macOS with Unity 6000.0.x | High. Needs a Unity project and a second build | Only for a large designed UI |

**Facts behind this table (checked in the game files):**

- **Input:** the game is set to "Both" input systems.
  - Old `UnityEngine.Input`, IMGUI, BepInEx `KeyboardShortcut` and text fields all work.
  - The game itself reads keys through `ZInput`.
- **Clicks:** each game scene has one EventSystem using the new Input System
  (`InputSystemUIInputModule`). A new canvas with a `GraphicRaycaster` gets clicks with no extra
  setup. (verified in ValheimTomrer)
- **Fonts:** the game's default TextMeshPro font is empty. Any text we create in code shows nothing
  until we set `.font`. (verified in ValheimTomrer)
- **Size:** add the game's `GuiScaler` component to our canvas, so our UI follows the player's "GUI
  scale" setting. The HUD's canvas has one too (measured).

## What to use for what

| Need | Best way | Effort | Tested in game |
|---|---|---|---|
| Info when looking at an object (a station, a chest, a door) | Add lines to the hover text (patch `GetHoverText`) | Easy | no |
| Short events ("Saved", "Too far away") | `MessageHud.ShowMessage` (center or top left), or the unlock card | Easy | center, through `Player.Message`: yes |
| A status that is always visible | An icon in the vanilla status row, or our own small text on the HUD | Easy to Medium | own HUD text: yes |
| A spot on the map | Map pin with `save: false`, plus a radius circle | Easy | no |
| Floating text over a point ("+1") | `DamageText.AddInworldText` (private method, local only) | Easy | no |
| Speech bubble over an object | `Chat.SetNpcText` | Easy | no |
| Yes/No, OK, or type-a-name dialogs | `UnifiedPopup`, the game's own popups | Easy | own popup type with own buttons: yes. Built-in `YesNoPopup` and others: no |
| A long report | A new page in Inventory > Texts | Easy | no |
| Info on a vanilla panel (the build card) | Postfix the method that fills it, change its fields | Easy to Medium | yes |
| Own controls in the key hints row | Own group under `KeyHints`, copies of the game's entries | Medium | yes |
| A list, picker, editor or settings window | Our own window (checklist below) | Medium | yes |
| A button in the Esc menu or main menu | Copy a vanilla button | Medium | no |
| Debug info | A console command, or IMGUI | Easy | no |

**Do not use these.** They send network messages:
- `Chat.SendText`, `Chat.SendPing`
- `DamageText.ShowText`
- `MessageHud.MessageAll`
- `Player.MessageAllInRange`
- map pins with `save: true`

## Own window: checklist

Details and code are in the [game API reference](19-09-2026-custom-ui-game-api.md#2-own-windows).

1. **Canvas.** Create one under the game's `IngameGui` object (the parent of `Hud`).
   (verified in ValheimTomrer)
   - Components: `Canvas` (screen overlay, own sort order about **950**), `CanvasScaler` (constant
     pixel size, reference pixels per unit **50**), `GuiScaler`, `GraphicRaycaster`, `CanvasGroup`,
     `UIGroupHandler`.
   - Order matters twice: `CanvasScaler` before `GuiScaler`, `CanvasGroup` before `UIGroupHandler`.
     The second of each pair reads the first in `Awake`.
   - Order 950 sits over the inventory and the store, under the center messages, text entry, the Esc
     menu and popups.
2. **Look.**
   - Panel: `Image` with the game's `woodpanel_*` sprite, sliced, `pixelsPerUnitMultiplier = 1`.
   - Text: `TextMeshProUGUI` with the font copied from a vanilla text, and **our own copy of its
     material**. (corrected: the HUD's hover-name material makes 12 to 16 point text read grey
     whatever its colour; the template's kit does this in `src/Ui/UiTheme.cs`)
   - Buttons: copy a vanilla button, or build one with the `button` sprite (the template's kit builds
     them in `src/Ui/UiBuild.cs`).
   - A row that carries text on the pale `item_background` sprite: tint the sprite dark, or white
     text on it is white on white. A `Button` on it needs `Selectable.Transition.None`, or its colour
     change tints it a second time. (verified in ValheimTomrer)
3. **Block game input while open.** One flag (the template's kit: `src/Ui/ModUi.cs`), plus nine
   patches (the template's kit: `src/Patches/InputBlockPatches.cs`):

   | Patch | What it stops |
   |---|---|
   | `Player.TakeInput` returns false | Attack, use, hotbar keys, building |
   | `PlayerController.TakeInput(bool)` returns false | Walking, looking |
   | `TextInput.IsVisible` returns true | Most game checks at once: Esc menu, map key, chat, zoom, crosshair. Also frees the mouse cursor. |
   | `InventoryGui.Show(Container, int)` is skipped | Tab opening the inventory |
   | `HotkeyBar.Update` is skipped | Pad D-pad using hotbar items |
   | `Menu.Update` is skipped | Esc and the pad's menu button opening the pause menu |
   | `Minimap.Update` is skipped | The map key |
   | `GameCamera.UpdateMouseCapture` postfix | Sets the cursor every frame: free, or locked when the window wants mouse look |
   | `ZInput.Internal_GetMouseScrollWheel` returns 0 | Mouse wheel zooming the camera. Our lists still scroll. |

   (corrected: the first plan had only four: `TextInput.IsVisible`, `InventoryGui.Show`,
   `HotkeyBar.Update` and the wheel. ValheimTomrer ships all nine: each effect is blocked directly,
   not only through the game's `TextInput` check, and the `Menu.Update` and cursor patches give the
   mod control of Esc and the cursor.)
4. **Close.**
   - When: Esc or pad circle (B). A text box that is typing gets its Esc first (step 7).
   - Keep the flag true for one extra frame, so the same Esc press does not also open the pause menu.
     (verified in ValheimTomrer)
   - After closing: `UITooltip.HideTooltip()`, `PlayerController.SetTakeInputDelay(0.2f)`,
     `ZInput.ResetAllButtonStates()`. (verified in ValheimTomrer)
5. **Close automatically** when the player dies, teleports or a cutscene starts. While the console,
   chat or a `UnifiedPopup` is up, do nothing: they handle their own Esc. (verified in ValheimTomrer)
6. **Gamepad.**
   - `CanvasGroup` + the game's `UIGroupHandler` (priority about 5). `m_defaultElement` may stay
     null: the handler then does nothing. (verified in ValheimTomrer)
   - **The EventSystem already has a vanilla button selected when our window opens** (measured: a
     build menu button). Clear it, or the first cross or Enter presses that vanilla button.
     (verified in ValheimTomrer)
   - **The game's UI module reads a real pad.** If our code also reads the pad, anything of ours
     selected in the EventSystem gets each cross press twice. Pick one: let the module drive
     (selected buttons, explicit navigation), or keep the EventSystem selection null and call
     `onClick.Invoke()` ourselves. Never both. (ValheimTomrer does the second; the double press
     itself was not checked by hand)
   - Set navigation with the game's `GuiUtils.SetNavigation*` helpers.
7. **Text boxes.** (all verified in ValheimTomrer)
   - The UI module sends a real pad's cross, circle and D-pad to a typing box as Submit, Cancel and
     Move. A plain `TMP_InputField` then submits on cross. Use a subclass that ignores `OnSubmit`,
     `OnCancel` and `OnMove` (the template's kit: the text box in `src/Ui/UiBuild.cs`). Typed keys
     still work: Enter submits, Esc puts the old text back.
   - The build menu clears the UI selection on every switch between keyboard and pad
     (`BuildUi.OnLayoutChanged`), so a typing box loses the keyboard. Skip it while the window is open
     (the template's kit: `src/Patches/BuildUiOnLayoutChangedPatch.cs`).
   - The box reads its keys in the game's UI update, which can run before our `Update` in the same
     frame. Treat "typing now or last frame" as typing, or the Esc that stopped the typing also closes
     the dialog.
8. **World reload.** The game rebuilds its UI and the `Hud` on every world load. Create our canvas
   lazily, check it with Unity's null check, and key caches on the live `Hud` object (the template's
   kit does this in `src/Ui/UiTheme.cs`). (verified in ValheimTomrer)

For simple questions, skip the window and use `UnifiedPopup`. It already blocks input, frees the
cursor, and handles keys and pad. ValheimTomrer pushed its own popup type with three buttons of its
own; the details and two traps are in the [game API reference, 2.8](19-09-2026-custom-ui-game-api.md#28-popups-unifiedpopup).

## What was checked in the game

**Verified in ValheimTomrer:**

| Item | How |
|---|---|
| Our window canvas shows up, with the recipe above | its editor window, every autotest run |
| A HUD element under `Hud.m_rootObject` hides with the HUD (Ctrl+F3) | a status line under it, and a list under the build card |
| Esc closes our window and does not also open the pause menu | one-frame grace, a key autotest |
| The mouse wheel scrolls our lists but does not zoom the camera | the window's lists and panels scroll |
| The pad D-pad moves through our window without using hotbar items | the `HotkeyBar.Update` patch, pad autotests |
| Sprite lookup by name (`woodpanel_trophys`, `button`, ...) in the world | nine sprites taken off `UIAtlas` |
| A new TMP text with no font shows nothing | its label builder sets the HUD's font on every text for this reason |
| Small text on the HUD's material reads grey | four rounds of "the text is grey", fixed with own material copies |
| The EventSystem has a vanilla button selected when our window opens | measured |
| A real pad's cross makes a plain text box submit | fixed with the text box subclass, proven by an autotest with a test pad the game's UI reads |
| The Esc that closes a popup also opens the pause menu in the same frame | own popup; fixed by skipping `Menu.Update` on that frame |
| The pad press that closes a popup reaches the game in the next physics step | circle jumped 1.4 m; fixed with `ZInput.ResetButtonStatus` |
| Filling the build card and taking over the key hints row | both shipped, both with autotests |

**Still unverified:**

- Pad cross pressing one of our buttons twice when the UI module AND our own code both act on it.
  Neither build does both: ValheimTomrer keeps the selection null and presses itself; the template's
  example window lets the module own the pad and binds no cross, and its autotest proves one cross
  is one press there (the test pad is a device the module reads). Check a real pad by hand once.
- A `UIGamePad` bound to A on a selected button firing twice.
- Our canvas following a change of the GUI scale setting while it is open (built with `GuiScaler`,
  like the HUD, but the setting was never changed during a test).
- Sprite lookup and a canvas in the main menu (ValheimTomrer builds UI only in the world).
- Everything marked "no" in [What to use for what](#what-to-use-for-what).
- `Localization.AddWord`, `TextInput.RequestText`, the built-in popups (`YesNoPopup`,
  `TextEntryPopup`, ...), pausing from our own window.

## Side finding

Since game version 0.221.4 the console (F5) is **off by default**. Turn it on in Settings > Gameplay,
or launch with `-console` (`Console.cs:28`, `FejdStartup.cs:590`).
